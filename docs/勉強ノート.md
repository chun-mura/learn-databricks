## レイクハウス = データレイク + DWH
- データレイク：CSVやログ、画像、動画などの多様な形式のデータを大量にそのままの形で保管できるシステム
- DWH：構造化データを分析しやすい形に整形し、BIツールなどから活用できるようにするための基盤
## 代表的なユースケース
  - 需要予測・レコメンデーション：在庫管理・販売戦略の最適化
  - IoT×異常検知・予知保全：センサーや工場データを元にした保全タイミングの予測
  - 大規模データ分析：不正取引検知
  - 顧客分析・パーソナライズ：マーケティング施策や顧客対応の個別最適化

# ADLS Gen2
## 参考

## 特徴
- Azure の大規模ストレージ。Databricks のデータ保存先として使う。階層型名前空間が特徴。
- ビッグデータ分析に最適化されたクラウドストレージサービス
- データレイクとしての機能（階層型名前空間など）を追加することで、大量のデータを効率的に保存・管理が可能
## 主な機能
### Hierarchical Namespace（階層型名前空間）
- 従来のデータレイクやBlobストレージが採用している`フラット型名前空間`と比較して、データ操作（コピー、移動など）が効率的
### Hadoop互換のACLとセキュリティ機能
- Hadoop互換
  - Hadoop分散ファイルシステム（HDFS）の操作をそのまま利用できる
- ACL
### 高いスケーラビリティとパフォーマンス
### データ解析ツールとの連携容易性
- Azure DatabricksやHDInsight、Synapse Analyticsなどのデータ解析ツールとスムーズに統合可能

# Delta Lake
- Lakehouseを実現する代表的なOSSのストレージレイヤー/テーブルフォーマット
- Parquetデータファイルをファイルベースのトランザクションログで拡張
- ACIDトランザクションとスケーラブルなメタデータ処理を実現するOSS
- Databricksに対するすべての操作のデフォルト形式。特に指定がない限りすべてのテーブルはDeltaテーブル。
## 参考
- [Databricks の Delta Lake とは何ですか?](https://docs.databricks.com/aws/ja/delta/)
- [Delta LakeとApache Spark™を用いた高信頼データレイクの構築](https://qiita.com/taka_yayoi/items/bcc69860a8073deb2cd4)
## 特徴
### オープンフォーマット
- blobストレージ上のParquetフォーマットとして格納される。
### ACIDトランザクション
- 複雑かつ同時実行されるデータパイプラインでデータの完全性と読み取りの一貫性を保証します。
### 監査履歴
- 予期しない書き込みをブロックすることでデータの綺麗さを保持します。
### タイムトラベル
- 時間あるいはバージョン番号による以前のバージョンのテーブルへのクエリー。
### deleteとupsert
- プログラミングAPIによるテーブルのdeleteとupsert（update + insert）のサポート。
### スケーラブルなメタデータ管理
- Sparkを用いることでメタデータのオペレーションをスケールさせ、数百万のファイルを取り扱うことができます。
### バッチ、ストリーミングソース、ストリーミングシンクの統合
- Delta Lakeのテーブルはバッチテーブルでもあり、ストリーミングのソースとシンクでもあります。ストリーミングデータの取り込み、バッチによる過去のバックフィル、インタラクティブなクエリー全てをすぐに活用することができます。

# Medalion アーキテクチャ
- 段階的なデータ品質の改善のために、データをブロンズ（生）、シルバー（クリーニング済み）、ゴールド（集約済み）レイヤーに整理するレイクハウス設計パターン
## 参考
- [メダリオンアーキテクチャとは何ですか?](https://www.databricks.com/jp/blog/what-is-medallion-architecture)
## パイプライン構築
### Delta Live Tables（DLT）
- 数行のコードでブロンズ、シルバー、ゴールドのテーブルでデータパイプラインを即座に構築できるツール（Databricksが提供）
### データレイヤーの役割
- ブロンズレイヤー：外部ソースからのすべての原始データ
- シルバーレイヤー：データをクレンジングして重要なビジネスエンティティに統合。第3正規形に近いデータモデル。
- ゴールドレイヤー：ビジネス分析用の製錬されたデータ

- エンドポイントにアクセスできるユーザーを制御します。
### 使用状況の追跡
- システムテーブルを使用して使用状況とコストを監視します。
### 推論テーブル
- `Unity Catalog Delta`テーブル内の要求と応答を監視および監査します。

- 使用状況をリアルタイムで監視します。

- エンドポイント、ユーザー、またはグループレベルで消費制限を適用します。

- コンテンツフィルタリング、機密データ保護、およびカスタムポリシーを適用します。

### 交通分離
- スケーラビリティと負荷分散を向上させるため、トラフィックを複数のモデルバックエンドに分散させる。
### カスタムAPIs
- カスタムAPIおよび外部APIs、LLMエンドポイントと同じアクセス制御、レート制限、およびログ記録で管理します。

# RAG
- Retrieval-augmented generatin（RAG）は、大規模言語モデル（LLM）とリアルタイムのデータ検索を組み合わせて、より正確で最新かつ文脈的に関連性のある応答を生成する手法。
## 参考
- [DatabricksのRAG(Retrieval Augmented Generation)](https://docs.databricks.com/gcp/ja/generative-ai/retrieval-augmented-generation)
## 仕組み
1. 取得
- ユーザーの要求は、ベクトルストア、キーワード検索、SQLデータベースなどの外部ナレッジベースに対してクエリを実行するために使用されます。
- 目標は、応答の裏付けとなるデータを取得することです。
2. 拡張
- サポートデータは、多くの場合LLMへの追加の書式設定と指示を含むテンプレートを使用して、ユーザーの要求と組み合わされてプロンプトが生成されます。
3. 生成
- プロンプトはLLMに渡され、ユーザーの要求に対する応答が生成されます。
![](https://docs.databricks.com/gcp/ja/assets/images/simple-rag-6c90ef4625802f288f45a004ebedf7f0.svg)
## データパイプライン
- [RAG用の非構造化データパイプラインを構築
](https://docs.databricks.com/gcp/ja/generative-ai/tutorials/ai-cookbook/quality-data-pipeline-rag)
1. コーパスの構成とインジェスト
- 特定のユースケースに基づいて、適切なデータソースとコンテンツを選択します。
2. データの前処理
- 生データを、埋め込みと取得に適したクリーンで一貫性のある形式に変換します。
  - 解析：適切な解析手法を使用して、生データから関連情報を抽出します。
  - エンリッチメント：追加のメタデータを含むエンリッチデータノイズの除去。
    - メタデータ抽出：有用なメタデータを抽出して、より迅速かつ効率的なデータ取得を実装します。
    - 重複排除：ドキュメントを分析して、重複または重複に近いドキュメントを特定して排除します。
    - フィルタリング：コレクションから無関係なドキュメントや不要なドキュメントを削除します。
3. チャンク化
- 解析されたデータを、効率的に取得できるように、より小さく管理しやすいチャンクに分割します。
4. エンベディング
- チャンク化されたテキストデータを、その意味的意味を捉える数値ベクトル表現に変換します。
5. インデックス作成と保存
- 効率的なベクターインデックスを作成しいて、検索パフォーマンスを最適化します。

### MLflow Projects
- 再利用可能なデータサイエンスコードを標準フォーマットでパッケージング。
- 依存関係やエントリーポイントを記述して、どこでも同じ手順で実行できるようにする（再現性・移植性の担保）。
### MLflow Models
- 学習済みモデルを「flavor」付きでディレクトリにパッケージングし、さまざまな環境にデプロイしやすくする。
- DockerベースRESTサーバ、Azure ML、SageMaker、Spark UDFなどへの展開をサポート。
### MLflow Model Registry
- 機械学習モデル版のGitHub
